## 2. 各阶段范围

### P-2 收尾（当前最紧急）

目标：让 Task 16 以**不放宽断言**的方式通过（P-2 完成标准第 5 条），然后合入。

工作项：

1. **诊断 AVERAGE 为什么 P1 要 63 天、P2 在 180 天内走不完**。先量化再调参：对 AVERAGE 在 day 63 与 day 180 各做一次 `evaluateGate` 阻塞分解——有多少 key 卡在 `stabilityThreshold`、多少卡在 `meanStepThreshold`、boss 替身是否过。按裁定 F 的思路，先找「结构性卡点」，再谈数值。候选怀疑点：
   - P2 的 T4 要求语境 L3，`demandOf` 对高语境题的难度项是否让阶梯长期撞地板（step 0），导致 `meanLadderStep` 上不去；
   - `PROMOTE_MEAN_STEP = 2` 与 `MIN_WINDOW_FOR_PROMOTION = 8` 是否让 `contextLevel` 升得太慢，而 P2 关卡又要求语境达标；
   - `GAIN_A`/`LOGISTIC_SLOPE` 两处未经裁定的改动，要么补裁定，要么回退后重新调。
2. ladderAccuracy 只差 0.009，很可能随第 1 项一并落进区间；**不要单独为它调参**。
3. 删除 `_tune4.test.ts`，把调参过程中真正有用的诊断（关卡阻塞分解、逐 key 轨迹）沉淀为 `runSimulation` 的导出诊断字段或一个独立的 `diagnostics.ts`，供日后回调参数用。
4. 补 FWD-P2-1 的断言（探针数恰等于 `min(可用级数, MAX)`），顺手做掉。
5. 订正账本（两处不实记录）与 T14/T15/T6 报告里的行数、分布错误（已记为 Minor）。
6. 提交、全分支终审（superpowers:requesting-code-review）、合入 master（superpowers:finishing-a-development-branch）。
7. **spec 写回**（§0.4 三条 + 前向约束补入 §16.2，编号 FWD-7 起）。

风险：若诊断表明普通学习者确实需要 >180 天才能到 P3，那是课程节奏与 spec §8.2 周期的冲突，要改的是 spec 的周期承诺或课程分级，不是断言。这种情况下要回到用户裁定，不能由执行者自行放宽。

### P-2b 题目生成器

目标：`generate(spec: ExerciseSpec, seed) → Exercise`，确定性，零 IO。

先决条件（开工前做完）：
- **FWD-2**：定下 `gain = baseVelocity × accentFactor` 之类的合成规则，并实现 `TimedOnset → NoteSpec` 桥接函数（放 `music/`）。
- **FWD-4**：在 `centerMidi` 入口做钳制（或对整个 `PlaybackPlan` 做音域钳制），测试覆盖 `variationLevel ≥ 3` 的极端组合。

范围：
- `Exercise` 类型：`{ plan: PlaybackPlan, prompt, answer, answerFormat, feedback }`。`answerFormat` 区分点选（选项集）、序列输入（听写）、唱（目标音级 + 目标频率区间，供 P-4）。
- 九类生成器：T/H/R × 听辨/唱/听写。每类的「题内参数」由 `difficultyStep`（0–5）映射：选项集大小、播放速度、旋律音数（听写 3–8 音）、音程跨度。映射表写成数据。
- `variationLevel` 0–6 逐轴开放（spec §6.2 表），`contextLevel` 0–4 接 `tonalContext`。
- H6 需要 FWD-3 的 voicing 函数（可与 P-5 一起做，但类型接口要在此定下）。
- R6 复合拍扩展前先读 FWD-6 的钉桩测试。
- 反馈内容（spec §6.4）作为 `Exercise.feedback` 的声明式数据产出：重放主音 + 刚才的音的 `PlaybackPlan`、慢速版 plan。渲染由 P-3 做。
- 答案校验函数 `grade(exercise, userAnswer) → { correct, detail }`，也是纯函数。

验收：
- 每类生成器固定 seed 快照测试；
- 属性测试：对任意 spec，`grade(exercise, exercise.answer)` 必为 true；plan 内所有 MIDI 落在可听范围；
- **集成守卫**：拿 AVERAGE/SLOW 仿真 180 天的全部 `SessionPlan`，逐道 `generate` 不抛错——这是 P-2 决策 3 承诺的那条测试。

### P-3 会话运行时、存储与最小 UI

目标：手机上打开即可按调度器真练一天，数据落盘，中断可续。这是第一个「可用产品」里程碑。

范围：
- `src/session/`：会话状态机（计划 → 出题 → 作答 → 反馈 → 下一题 → 结束），消费 P-2 的 `buildSessionPlan` 与 P-2b 的 `generate/grade`；阶梯续起逻辑从 `runSimulation.ts` 搬到这里成为正式实现（`resumeLadder`），仿真改为复用它；护栏（`needsRelief`/`relieveSpec`/`decompose`）接入；§6.5「重练刚才错的这组」；§11 中断处理（`AudioContext` suspend 后当前题作废重出，不计错）。
- `src/storage/`：`Repository` 接口；IndexedDB 实现（schema 带版本与迁移）；内存实现（隐私模式降级 + 测试用）；`Attempt` 全量留存（上限 5 万条后归档）；JSON 导出/导入；损坏时导出副本再重建，不静默清空。
- `src/ui/`：首次使用流程（周期明示 §8.5、耳机建议、分级测试 §7.7 消费 `placement.ts`、音域测定先做占位）；练习页（答题按钮在屏幕下 1/3、三种显示皮肤、§6.4 反馈：音阶条上同时标两个音级 + 慢速重听）；唱模态先用 §12 的**自评模式**（这使 P-3 不依赖 P-4 即可闭环）；今日总结页；设置页（显示皮肤、导出/导入）。
- Wake Lock、iOS 手势启动音频。
- 处理 FWD-1（`active` 修剪）、FWD-5（audio 层目标音前淡出）、§15.1（显示层语境拼写，`DisplayScheme` 按调式与方向决定）。
- 把 P-1 遗留的 10 项手机人耳实听补做，含 §16.3 的音色可分辨性；分不出则改 `oscType`。

验收：
- 真机完整跑一场 25 分钟会话；杀掉页面再打开能续；
- 存储层单测（含迁移、损坏路径）；

### P-4 视唱闭环

目标：唱模态从自评升级为真判定（spec §9）。

范围：YIN 于 AudioWorklet（48 kHz / 2048 / hop 512）；稳定段检测（约 150 ms）；中位数 f0 与目标的 cents 偏差 ≤ 50 判对；八度折叠；音域测定（替换 P-3 的占位）；3 秒噪声基线校准；目标音播放期间暂停采集；权限拒绝或 Worklet 不支持时回落到自评模式。

验收：合成已知频率的测试音频验证 YIN 精度；录制少量人声样本验证稳定段检测；真机男女声各测八度折叠。

可与 P-3 后半段并行：`pitch/` 是脏边界模块，接口 `detect(stream) → { f0, confidence }` 事先定好即可。

### P-5 实战关

目标：五个阶段的实战关从仿真替身变成真题（spec §8.2、§8.4）。

范围：多轨合成片段生成器（贝斯 + 和弦 + 旋律 + 简易鼓），全部 Web Audio；每阶段一类关卡题（P1 八小节五声旋律听写 + 拍号；P2 十六小节大调听写；P3 四和弦循环 + 旋律；P4 流行歌片段扒谱；P5 转调片段）；FWD-3 的 voicing 函数在此必须落地；`evaluateGate` 的 `bossPassed` 入参改由真实关卡结果提供；鼓类音色需新增 1–2 个合成音色。

验收：每阶段关卡固定 seed 快照；仿真改用真实关卡的「可答性」检查替换 `BOSS_ABILITY_THRESHOLD`。

## 3. 建议的开工顺序与近期动作

按优先级：

1. **本周：P-2 收尾。** 先做 §2「P-2 收尾」第 1 项诊断，带着数据回来裁定，再调参或改结构。不要在没有阻塞分解的情况下继续盲调常量——账本显示上一位执行者已试了 30 多种组合。
2. **P-2 合入后：spec 写回**，同一个 PR 或紧随其后的 docs 提交。
3. **然后：P-2b 的 brainstorming → writing-plans。** 先在 brainstorming 里定下 `Exercise` 类型与 `answerFormat` 的形状、`difficultyStep` 到题内参数的映射表、FWD-2 的合成规则——这三样是 P-2b 与 P-3/P-4 的接口，定错了后面都要返工。
4. P-2b 实施期间可并行起草 P-3 的存储层接口（`Repository`），它不依赖生成器。

每个阶段的「完成标准」沿用 P-1/P-2 的格式：vitest 全绿、tsc 干净、vite build 成功、新增目录零 IO 自查、验收物逐条可演示。
